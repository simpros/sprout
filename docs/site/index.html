sprout

Every pull request gets its own preview

Sprout gives every pull request an isolated database and a live preview app — for teams that want to review running code, not just diffs. You host one shared instance; sprout handles the per-PR isolation and cleans up when the PR closes.

How it works

An operator deploys the shared instance plus the sprout gateway once. An adopting repo adds one config file and calls sprout from CI. Each pull request then lives through the same five steps:

create → migrate (app) → seed (optional) → hand over → drop PR opened / synchronize PR closed │ │ ▼ ▼ sprout deploy ──────────────────► sprout teardown │ │ ├─ CREATE DATABASE ├─ stop app / seed / services │ sprout_<slug>_pr<id> └─ DROP DATABASE ├─ start app container │ + Traefik Host labels └─ optional seed image (after health check) │ ▼ preview URL for this PR

1. Create

Opening a PR creates its own logical database on the shared instance.

2. Migrate

The preview app starts against that database and runs its own migrations.

3. Seed

Optional demo data loads once the app reports healthy.

4. Hand over

Reviewers open the preview URL. Pushes redeploy into the same database.

5. Drop

Closing the PR stops everything and drops the database. Nothing lingers.

Why it is cheap to run

The resource argument is the whole pitch: one shared Postgres instance serves every pull request. Each PR gets one logical database on that instance — real isolation without provisioning a database server per PR, and without paying per-environment platform fees. When the PR closes, its database and containers go away.

  • One server, many previews. Isolation is a logical database per PR, not a cluster per PR.
  • Light repos stay light. SQLite-file previews and no-database previews cover frontends, workers, and services that need no Postgres at all.
  • No lock-in. The gateway and the database run on infrastructure you already operate, next to your existing reverse proxy.
  • Nothing lingers. Teardown on PR close is the normal path; a periodic sweep recovers anything CI missed.

What a preview gives you

  • A live app URL for the PR, served through your own Traefik routing.
  • Seeded data so reviewers click through a working product, not an empty shell.
  • Companion services — workers and secondary APIs that share the same preview database.
  • Optional mail — previews send test mail into a shared inbox, addressed per PR so testers can tell them apart.

How each of these is configured lives in the docs: previews for the lifecycle, operator deploy for the shared side.

FAQ

Does sprout replace our hosting?

No. It adds per-PR previews next to whatever you already run. Your production setup stays untouched.

Do we need webhooks from our forge?

No. CI on PR open, push, and close drives the lifecycle; a sweep recovers anything CI missed.

What happens to data when the PR closes?

The preview database and its containers are removed. Pushes to an open PR keep the same database; only closing drops it.

Our repo has no database — is sprout overkill?

No. Light repos run SQLite-file or no-database previews: same preview URL and lifecycle, without a Postgres database.

Can two PRs see each other's data?

No. Each PR gets its own database (or its own file volume), so reviewing one PR never disturbs another.
